# Lab drift notes (generated)

Generated by `scripts/lab_drift.py` from `data/flows/lab_flows.csv` (source `pq_lab`): 15300 flows, 18 profiles (kem | auth | chain). Feature lists: `pqdl.features` version `3`. Reference profile for PSI and MMD: `X25519|ecdsa_p256|leaf_int`. Full numbers: `results/lab_drift.csv`.

## Caveats

- **Single lab topology.** One client and one server container on one Docker network, on one laptop. Nothing here says how the effects look on a real path.
- **Local network.** No real RTT, jitter or loss: timing features reflect scheduling on one machine, and retransmissions essentially do not occur.
- **Session tickets are disabled** (`-no_ticket -num_tickets 0`), so no NewSessionTicket records appear after the handshake. A deployment with tickets would add bytes to the application phase of every profile.
- **Pinned groups and signature algorithms.** Each profile pins exactly one KEM group and one signature algorithm on both sides; real clients offer many and servers choose.
- **Benign workloads are scripted** (seeded file requests with fixed sizes and pauses), the two attack-like workloads are scripted too. They are far from real traffic and from each other, so any detector separates them easily.
- **Same seed for every profile** (1234). Each profile's workload sequence is identical, so differences between profiles are not caused by different request mixes, but the lab does not average over seeds.
- **Packet features are valid only with NIC offloads off** (`capture_offload_ok`); the analysis refuses to run if any pcap says otherwise.
- **Statistical yardstick, not a test.** `noise95_*` is the 95th percentile of the statistic when profile labels are randomly permuted within a workload; a feature is called 'not invariant' when its effect size exceeds it. It depends on the sample size per profile (benign 300, flood 200, slow_send 50 flows).
- **A profile is one pcap per workload, so profile and pcap are confounded.** Anything that changed between pcaps (laptop load, scheduling, position in the run) is perfectly mixed with the crypto profile. The permutation noise floor shuffles flows, not pcaps, so it cannot see pcap-level effects and understates the noise of timing features. Byte and packet-count features are not affected (they are fixed by the workload and the handshake), but timing effects (IAT, durations) cannot be attributed to the profile without replicate captures of the same profile.
- **First-ten packet sizes** (`app_*_size_k`): a missing k-th packet is entered as 0 for this analysis. Other NaN statistics (for example IAT with fewer than two packets) are dropped feature by feature, and rows with any NaN are dropped from the MMD.
- **One cipher suite** in the data: 0x1302 (every connection uses the same AEAD, so record overhead is identical across profiles; another suite would change record sizes).
- **1 benign_web pcap(s) flagged for timing:** `X25519MLKEM768|mldsa65|leaf_int` (started 2026-11-24T07:39:36Z, median 3.72 ms, 3.39 MADs from the median of profile medians). Timing may have been disturbed by activity on the laptop; cause unknown. No data was dropped, so timing-based features for that profile (`hs_duration`, `app_duration`, `app_iat_*`, `flow_duration`, `flow_iat_*`) should be read with care.

## H1: what explains handshake drift (kem x auth, chain = leaf_int)

Partial eta squared per term. `hs_*_bytes`, `hs_*_pkts` and `hs_records` are usually exact functions of the profile: zero spread inside a (kem, auth) cell, so there is no residual and their partial eta squared is trivially 1 for any factor that changes them (and 0 otherwise). The informative rows are the non-deterministic features (timing).

**Byte features with a few bytes of spread inside some cells** (listed as non-deterministic on purpose): hs_s2c_bytes (max within-cell std 0.775 B). The cause is the ECDSA cells: ECDSA signatures are variable-length DER (70-72 bytes), so the CertificateVerify and the certificates' own signatures change the handshake size by a few bytes from connection to connection, and each pcap ran on a freshly generated PKI. ML-DSA signatures have fixed length, so those cells have zero spread. The spread is a tiny fraction of the between-cell differences, so the partial eta squared of these features stays close to 1: read them as near-deterministic, not as timing-like noise.
